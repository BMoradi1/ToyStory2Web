================================================================================
 THE SHORT ANSWER
================================================================================
 Use Fable for reading the 1999 executables. Use Opus for everything else.

 The split is not "hard vs easy". It is whether the work is DECODING - forming
 a hypothesis about unlabelled data and testing it against an oracle - or
 IMPLEMENTATION, where the answer is already written down and the job is to
 type it in correctly.

 Every real find this session came out of decoding, and each one changed the
 plan rather than following it:

   - the level material table, read from Direct3D render-state calls in
     toy2.exe rather than guessed from PSX conventions
   - "the second object section has a different record layout" - wrong. It has
     the SAME layout at a quarter scale. Seeing that took holding a failed
     hypothesis loosely
   - "objects only correlate 65-72% between the two files, so we may need to
     switch render source" - wrong, and the decision it implied was never
     needed. The mismatch was our own parser bug
   - the visibility algorithm, lifted whole out of the portal walk

 The implementation that followed each of those was routine, and Opus did it:
 blend modes and culling in three.js, zone bucketing and filtering, the
 collision query, standing Buzz on the floor, the docs.

================================================================================
 IF YOU ARE THE MODEL READING THIS
================================================================================
 You are expected to say when you are the wrong model for what is in front of
 you. Neither switch is a failure; carrying on regardless is. The switch costs
 the user one line, so the bar for suggesting it is low - but say it plainly
 rather than hedging, and say which way.

 Switch does not mean stop. Finish or park what you are on, write down what is
 settled and what is not, then say what the next model should pick up. The
 handoff line is the boundary between "what IS this" and "make it so", not the
 boundary between hard and easy.

 --- ON OPUS, ASK FOR FABLE WHEN ---------------------------------------------
   - you are about to guess. A constant, a field offset, what a flag bit
     means, which of two readings is right. Guessing and moving on is how the
     quarter-scale bug survived from the very first commit to this one
   - a test of your hypothesis half-works. 60-90% agreement is the signature
     of a WRONG MODEL, not of noisy data. This session's "objects only
     correlate 65-72%" was a parser bug, and reading it as a correlation
     problem produced an architectural decision that never needed making. A
     clean rule scores ~100% or ~0%; anything in between means look again
   - you are reading disassembly or decompiled C to find something that has
     no name yet
   - two files that describe the same thing disagree and you cannot say which
     is right
   - you catch yourself writing "probably", "seems to", or "consistent with"
     in a doc or a commit message about something you have not tested

 --- ON FABLE, HAND BACK TO OPUS WHEN ----------------------------------------
   - the unknown now has a written-down answer with a validation number
     attached, and what remains is wiring it in and checking it looks right
   - you are about to write renderer code, tools, tests or docs around a fact
     that is already settled
   - you have been going for a while without a new hypothesis, and the next
     step is mechanical: running a validator over every file, updating call
     sites, tidying an interface
   Do not hold on to a task because it is nearly done. Hand over at the answer.

 --- HOW THIS ACTUALLY WENT --------------------------------------------------
 It worked twice in the Phase 1 session, in both directions. Opus, doing
 routine implementation, hit the 65-72% correlation figure, reported it as an
 anomaly instead of working around it, and asked. Fable found that it was a
 parser defect placing a quarter of every level wrong, fixed it, and handed
 straight back at the point where the rule was known and validated. Neither
 model finished the task it started. That is the pattern to copy.

 The Phase 2 session is a correction to the rule, and worth reading before
 trusting it. P2.5, the animation mapping, was written down here as Fable work
 on the reasoning that finding an unnamed structure by shape is decoding. It
 took Opus one grep, because the animation state machine sits one call away
 from a function P2.1 had already named. The lesson is not that the split is
 wrong; it is that the cost of LOOKING is much lower than the cost of decoding,
 so look first and route afterwards. Spend ten minutes before declaring
 something a Fable job.

 The same session also shows the failure the split is meant to catch, in the
 other direction. Opus assumed which way character models face, "verified" it
 with a test that could not fail (the camera was placed behind Buzz by
 construction, so of course it saw his back), and shipped him running
 backwards. Nothing about that needed a stronger model - it needed a test that
 could come out either way. When a check confirms what you already believe,
 ask what result would have disproved it.

 WHAT TO GIVE FABLE, IN ORDER
================================================================================

 1. WHAT IS LEFT OF PHASE 2.  P2.1 through P2.5 are done or part done; the
    remaining pieces are all ordinary work and none of them need Fable.

    The camera's four modes, auto-centring and look-ahead (FUN_004045e0 is
    4.7 KB and only its skeleton is ported - the module lists exactly what was
    left out). The twenty animation states that belong to moves that do not
    exist yet. The footfall and sound opcodes, which are counted but not
    played and are the cheapest audio hook in the project.

    Then Phase 3 and beyond: the HUD, enemies, the save file.

 2. THE LEVEL SCRIPTS - now defined and readable (2026-09-05, docs/LEVELS.md).
    Init/tick per level via two jump tables, tasks via shared helpers, the
    five token slots mean the same thing everywhere. What a Fable pass should
    do next, in order:
      - (the creature system is DECODED 2026-09-05: docs/CREATURES.md.
        Placements come from levelNN/level.raw record 0x23 - the .raw is
        an RNC method-2 packet, unpacker ported and CRC-validated - and
        behaviour is a word-code interpreter over 44 scripts in the exe,
        extracted to src/sim/creature-data.ts. The eight handlers the
        first pass missed are defined now. 2026-09-05 later: the hit
        ellipsoids are the model's trailing type-9 .all group
        (readHitShapes), the entity's centre offset and hit radius are
        that group's entry words, and animState indexes the .anm slot
        table directly - so creatures can be drawn and hit-tested from
        the files. Record 0x24 is the level backdrop image, 192 x 128
        paletted, the .ngn's bgr36; nothing is left on this item.)
      - (the two per-level tables are DECODED 2026-09-05: FUN_004025c0
        loads the HINT SIGNS and FUN_00402610 opens their talk box - the
        "camera trigger" was a tutorial signpost; FUN_004335d0 loads the
        PUSH BLOCKS. Both in docs/LEVELS.md with the talk script, the
        camera flight and the text box; tables in src/sim/level-data.ts,
        validated against every scene. Side find: a dynamic collision
        group's object number sits at +0x1a of its TERRAIN.ALL entry;
        reserved path tags 58 (sparkle points, decoded) and 59-63 (leads).)
      - (the sound event pitch is SETTLED 2026-09-05: unused on PC, the
        buffer plays at the WAV's own rate. The attenuation, pan and
        slider maths are in docs/LEVELS.md "Attenuation, pan and the
        slider"; Opus can port playEvent() now.)
      - (the wall-line list DAT_007290f4 is CLOSED 2026-09-05: the machine
        code never writes it - zeroed at level load, read three times -
        so the line collision is dead on PC. docs/PLAYER.md.)
      - THE EFFECT SYSTEM. This is the one thing on the whole list that
        an Opus pass should not attempt, and the reason is measured
        rather than felt. What is settled, from a read on 2026-09-05:

          * the records are 0x3c bytes at DAT_00529e58, spawned by
            FUN_0040fae0(x, y, z, vx, vy, vz, a, b, c, kind) and updated
            by FUN_00410f40
          * the spawner writes position at +0, velocity halved at +0xc,
            and then COPIES thirteen bytes out of a 16-byte per-kind
            template at 0x4ec160 into +0x24..+0x3a, doing no arithmetic
            on them. A second table at 0x4ec948 (0x18 bytes) supplies
            randomisation modes 1..6 for the velocity
          * 127 of the template rows are non-empty, so there are 127
            effect kinds
          * kinds seen at call sites: 0x3d the creature death burst,
            0x26 the hover bot's shot, 0x23/0x11/99 death sparks,
            0x71/0x73 the sparkle points on path tag 58, 2 the push
            block's dust, 0x7e/0x7f a pair spawned together

        What is NOT settled is what any of those thirteen template bytes
        MEAN. Their only definition is FUN_00410f40 itself: 912 lines of
        decompiled C with 60 case labels. Working them out is forming a
        hypothesis about unlabelled data, and the oracle is weak -
        particles are visual, there is no .ngn copy to join against, and
        a wrong reading yields something that looks plausible and is
        wrong. That is exactly the failure this split exists to catch.

        Porting it unlocks a lot at once: the laser bolt (damage kind 4,
        which the creature code already handles), the hit sparks and
        death bursts the creature port raises but cannot draw, the hover
        bot's shots, and the sparkles over unspent secrets.

      - WHICH ZONE THE PLAYER IS IN. Small, and it blocks more than it
        looks like it should. Every level's tick is written per zone,
        and eight of the nine boss fights start on a zone test: level 5's
        is "the player is in zone 2, then taunt, then kick the boss's
        script to word 14". Level 1's boss is the exception - its trigger
        is a height band - which is why it is the only one that can be
        started so far.

        What is settled: `FUN_00440f70` sets the player's zone from
        `FUN_004885c0(camera position)`, and that walks the collision
        objects, finds the nearest surface below the point, and returns a
        byte at `DAT_007295d6 + object * 0x1a`. So a zone is a property of
        the collision surface you are standing on, not a region of space.

        What is not: where the collision loader (`FUN_00489c30`) gets that
        byte. It is not an obvious field of the `.all` group entry - the
        only bytes there that vary over a small range are the object
        number at +0x1a, already identified, and the LOD bits at +0x29.
        Finding it is a field hunt over unlabelled data, so it is a Fable
        job rather than a guess; the wrong guess would make bosses taunt
        in the wrong rooms.

        Everything else about the boss fights is ported and waiting on it:
        each level's boss creature, its script's wake word (14 everywhere
        but level 4, which is 12), and the token award.

        One more thing waits on the same byte, found 2026-09-05: level 7's
        timed egg run is supposed to fail the moment Buzz leaves the area,
        which its tick writes as "zone 4 slams the clock to 99". The run
        itself is ported and works; that one rule is stubbed out behind a
        `failZone` field, so the byte switches it on with no other change.
        Nothing else about the timed tasks is open - the run state, the
        clock's floor of 100 and its 1-in-64 frame divider are all written
        up in docs/LEVELS.md.

      - nothing else is left on this list. The rest is item 3.
        For the avoidance of doubt, the token tasks are FINISHED as far as
        decoding goes: all five slots on all ten non-boss levels are ported
        and tested in the browser, and the only gap in them is the zone
        byte above.

 3. THE REMAINING FORMAT UNKNOWNS.  None block anything, all are the same
    shape of puzzle, and the .ngn scene is an oracle for most of them:
      - (the "sprite pool" is DECODED 2026-09-05: sprite records - nodes
        carrying camera-facing cards - interleaved with the meshes, told
        apart by the placement's flags; docs/FORMATS.md, DatSprite. The
        PSX decompile, rebuilt this session, gave the draw semantics.)
      - (section 4 is SOLVED 2026-09-05: two placement tables and the

      - (the extra-pass material is DECODED 2026-09-05: a reflection pass,

 MUSIC - decoded 2026-09-05.  Nothing left to
 find; this was a wiring job against src/audio/sfx.ts's GameDir handle.

   Files: audio/<name>.wav in the install root (NOT data/), plain PCM WAV,
   about 8 MB each. Twenty-two names, in the order of the table at 0x4eccd8
   (FUN_00413150 builds "audio\" + name + ".wav" and hands it to a
   DirectShow thread, FUN_00436ce0 -> FUN_00413240):

     0 house     1 neighbou  2 buzvred   3 constr    4 alley
     5 slime     6 als_toyb  7 spacelnd  8 buzvbuz   9 elev
    10 als_pent 11 buzvzurg 12 convey   13 tarmac   14 buzvpros
    15 miniboss 16 minirace 17 over     18 complete 19 ygafim
    20 titlescr 21 levcomp

   Index 0..14 IS level-1: the level's track is the table entry at the
   0-based level index (DAT_0052ad8a), so level 1 plays house and level 15
   buzvpros. music21.wav and fullhouse.wav on disc are unreferenced.

   Selection (FUN_0049eac0, called from each level's tick):
     if the mini-boss timer DAT_0052c832 != 0     -> 15 miniboss
     else if racing (DAT_0052c830 != 0 and the race state DAT_0052f2f8 is
        2, i.e. started and not finished)          -> 16 minirace
     else                                          -> the level track
   Each branch only restarts when the current track (DAT_00559c68) differs,
   so it is a "want this playing" call, safe every tick. The creature code
   sets the mini-boss timer to 0x5a (90 ticks) while a mini-boss is live.

   Looping: FUN_0047d880(track) plays looped (loop flag 1) - all of the
   above plus 19 ygafim on the front-end menus and 18 complete on the
   game-complete screen. FUN_0047d7f0(track) plays once: 17 over on game
   over, 20 titlescr on the title, 21 levcomp on the level-complete screen.
   Starting a track stops whatever is playing first. Pause/resume replays
   the stored current track.

   Volume: the options slider is 0..64 (DAT_005282c8). FUN_0049ae40 maps it
   through a 151-entry curve at 0x4fd668 (index = slider*150/64) giving
   DirectShow volume in 1/100 dB: -10000 (silent) at 0, -1126 at slider
   ~26, -103 at ~51, 0 from ~60 up. For the Web Audio gain use
   10^(dB/2000). Sound effects use a separate slider.

   Suggested port: a MusicPlayer next to SoundBank with play(track, loop)
   and a want(track) that no-ops when it is already the current track;
   decode with decodeAudioData (8 MB WAV is fine) or stream through an
   <audio> element from a blob URL, which avoids holding the decoded PCM.
   main.ts calls want(level-1) after spawn, and the race/mini-boss overrides
   land when those systems exist.

================================================================================
 THE METHOD THAT KEEPS PAYING OFF
================================================================================
 Every level exists twice on the disc: level.dat is the PlayStation scene and
 level.ngn contains pconv's conversion of it. That redundancy is the single
 most useful thing in the install. The converted copy has already resolved
 what level.dat leaves implicit - materials, zone assignments, per-vertex
 alpha - so it can be used as an ANSWER KEY for the original.

 Both the material table and the quarter-scale bug were found by joining the
 two files and looking at where they disagreed. When something in level.dat is
 ambiguous, reach for the .ngn before reaching for a theory.
 tools/scene-crosscheck.ts is the harness for this.

 The other habit worth keeping: build the oracle before the feature.
 tools/render-level.ts rasterises the same geometry offline and
 tools/browser-shot.ts drives the real viewer headlessly, so a change can be
 diffed pixel against pixel. The car-quarter bug and the colour-space bug were
 both invisible by eye and obvious in a diff.

 A TRAP THAT COST TWO COMMITS.  Do not run

   pkill -f "vite --port 5173"

 The pattern matches the shell's own command line, so the shell kills itself
 and everything after it in the chain silently does not run. It swallowed a
 commit twice before I noticed - and then a third time with "bin/vite", which
 is no better: ANY literal pattern appears in the command line that runs it.
 The only safe form is one the shell text cannot match, e.g.

   kill $(pgrep -f "[b]in/vite")

 where the bracket makes the regex match "bin/vite" but not the literal
 characters "[b]in/vite" in its own invocation. Run it on its own line.

 ANOTHER TRAP.  .gitignore has a bare "game/" rule (it guards against a copy
 of the install landing in the tree). It also ignores src/game/, silently -
 a module written there never showed in git status. Game logic lives in
 src/sim/ for that reason. Do not weaken the ignore rule.

 GIT.  The repo is on GitHub and you are not the only one committing to it -
 branch main was renamed and relicensed mid-session, and three README commits
 appeared from elsewhere. Fetch before assuming your view of origin/main is
 current, and never force-push.

 The one exception, 2026-09-05: every commit message carried a
 "Claude-Session: https://claude.ai/code/session_..." trailer, and the user
 asked for those links to be removed from the repo. The 44 affected messages
 were rewritten with git filter-branch and force-pushed, which changed the
 hash of all 57 commits from 092e90c onward - the tree at the tip was checked

 "git reset --hard origin/main". DO NOT ADD THAT TRAILER AGAIN: commits end
 with the Co-Authored-By line and nothing else.
