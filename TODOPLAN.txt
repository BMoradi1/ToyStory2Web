 HOW TO USE THIS FILE
   Work top to bottom. Phases are ordered by dependency, not by appeal.
   Anything marked [BLOCKED] names what it waits on. Update status markers as
   you go and keep docs/FORMATS.md in sync when a format is cracked.

 STATUS
   [DONE]      finished and verified
   [ACTIVE]    in progress right now
   [READY]     unblocked, nobody on it
   [BLOCKED]   waiting on a named dependency
   [OPEN]      not yet understood; research needed

 THE THREE RULES (see CLAUDE.md)
   1. No game assets in git, ever. Users supply their own copy.
   2. "Toy Story 2/" is read-only. It is the user's only copy.
   3. Never call a format solved without parsing it end to end and validating.

================================================================================
 STRATEGY
================================================================================
 A decompilation-guided rewrite in TypeScript, driven as a VERTICAL SLICE
 through level 1, with the original game as the oracle at every step. Not a
 MIPS interpreter, not an emulator.

 WHY THIS SHAPE
 - toy2.exe (1.29 MB, x86) is a native build of the same C source, on
   Traveller's Tales' NU engine. Its assert strings name the modules:
   nu3d/world.c, objcore.c, objload.c, hobjload.c, fmv.c, toy2/toy2.cpp,
   direct6.cpp, modesel.cpp. It is the reference: x86 decompiles well in
   Ghidra (installed at /usr/bin/ghidra), and its Direct3D calls state the
   material system outright - whichever mode bits become blend and cull
   render states ARE the answer, no PSX GPU inference needed.
 - psx.exe / SLUS_008.93 are the same logic for MIPS. Use them to cross-check,
   with PeriBluGaming/ToyStory2Recomp's 658 entry points to seed Ghidra (they
   are bare addresses, not names).
 - The game runs locally under dgVoodoo. Side-by-side screenshots are
   available whenever wanted; the browser-shot tool makes ours reproducible.
 - A MIPS interpreter would need the engine import surface (100-300
   functions) implemented anyway - that IS the reimplementation, with an
   interpreter as dead weight on top. Rejected.

 RULES THAT KEEP IT HONEST
 - Level 1 is the only level until it is complete. Everything is discovered
   there; the other 14 are data plus per-level logic once the pattern exists.
 - Every subsystem gets an oracle before it gets features. The renderer has
   two (tools/render-level.ts for geometry, tools/browser-shot.ts for what
   the browser does with it); the browser one is what caught the car.
 - Use the decompilation as a BEHAVIOURAL reference - constants, state
   machines, orderings - and write the TypeScript from understanding rather
   than transcribing it. That keeps the project publishable.
 - Parsers stay pure (Uint8Array in, plain data out), validated across the
   whole install by a tools/*-validate.ts script.

 A DECISION THAT NO LONGER NEEDS MAKING
   Rendering from level.ngn instead of level.dat was on the table because the
   .ngn carries zone assignments the .dat appeared to lack. It turned out the
   two files correspond one for one in order, so zones transfer by index and
   level.dat stays the render source. The .ngn remains invaluable as an
   ORACLE - it is how the material table and the object-table defect were
   both found - and worth reaching for whenever level.dat is ambiguous.
   Recorded so it is not reopened:
   level.dat is the PSX scene and is what this project parses today. pconv
   converted each level into an NU-engine scene inside level.ngn, and it is
   the .ngn that the PC renderer draws. (toy2.exe does also load level.dat at
   runtime, in InitLevelPlay, for something not yet traced - so it is not
   dead data on PC.) The scene carries
   what level.dat does not - zone assignments, resolved materials, per-vertex
   alpha, float transforms - and is the reason the material table could be
   decoded at all. Rendering from it would unblock visibility immediately and
   match the retail build exactly. Against that: level.dat is the original
   data, the parsers and every validation here are built on it, and the PSX
   version is the more faithful target for an engine reimplementation.
   Nothing needs deciding until P1.5, but P1.5 cannot finish without it.

 MAIN RISK
   How much of toy2.exe is game logic versus NU engine: the first Ghidra
   pass found 1,307 functions, cleanly split by assert strings into nu3d/*
   (engine) and toy2/* (game). The render side read easily; the gameplay
   side is untested.

 PHASE 1 - RENDERER TO PARITY
================================================================================
 Done means: level 1 matches a screenshot of the real game from the same
 camera, to within texture filtering.

 DIAGNOSIS (2026-09-03) - geometry was right; the four defects below were
 all downstream of it, and 1, 2 and 4 are now fixed:
 1. Colour management. three.js outputs sRGB, so vertex colours and
    DataTextures are brightened: (0,82,0) reaches the screen as (0,163,0).
    This alone is the "green panels": those mode 0x0070 panes are opaque
    dark green in the original too (confirmed from the PC scene data).
 2. Semi-transparent overlays drawn opaque. The faces that must blend are
    the ones with mode low byte 0x00-0x06 / 0x20-0x26 (vertex alpha 0x80);
    black half-blend shadows and additive glows. See FORMATS.md "Material
    system" for the full bit table.
 3. No visibility: all 22 zones draw at once. Zone quads are PORTAL PAIRS
    (each doorway twice, (a,b) swapped, b=15 = outside).
 4. No culling. Everything is one-sided in the original except bit-0x02
    faces; THREE.FrontSide is the right winding (verified on 199 floors).

 P1.1 [DONE]    Material table from toy2.exe. The PC build draws the NU scene
                inside level.ngn, not level.dat; pconv resolved every face
                mode into a material whose render-flag word the exe maps onto
                D3D states. Read the state cache (FUN_004b6320) and the flag
                mapping (FUN_004b6760) in Ghidra, then joined the .ngn scene
                to level.dat by vertex position across 16 files. Result in
                FORMATS.md; reproducible with tools/material-table.ts.
                Ghidra project + full decompile dump live in the session
                scratchpad, not the repo; rebuild with analyzeHeadless on
                toy2.exe (about 3 minutes) if needed again.
 P1.2 [DONE]    Raw colour pipeline. THREE.ColorManagement is OFF and output
                is LinearSRGB, so a stored byte reaches the screen unchanged;
                leaving either on brightened everything, and colour
                management still applied to THREE.Color values (the scene
                background) after the output transform was disabled.
                Textures are nearest for BOTH min and mag with no mip chain.
                Verified: untextured faces render at exactly their stored
                colour ((8,8,8) and (25,0,0) sampled pixel-exact), and the
                browser matches the offline oracle from the same camera on
                93% of flat interior pixels within 1/255, the rest being
                edge antialiasing, which the oracle does not do.
 P1.3 [DONE]    Blend modes. Draw groups are split by (page, blend,
                cull) rather than page alone - a wall and the glass in front
                of it can share a texture and still need different states.
                Opaque groups are emitted first, then normal
                (SRCALPHA/INVSRCALPHA), additive (SRCALPHA/ONE) and the
                three subtractive faces in the whole game, all at alpha 0.5
                with depth writes off. Level 1: 32,285 opaque, 464 additive,
                354 normal triangles. Cutouts stay in the OPAQUE queue with
                alphaTest instead - a deliberate divergence, since the
                original drew them blended with no depth writes, which needs
                exact back-to-front order to look right.
 P1.4 [DONE]    Culling. THREE.FrontSide, DoubleSide only where mode & 0x02
                (607 triangles in level 1). Roughly half of level 1's
                triangles are now culled. Characters stay double-sided:
                their parts are not closed shells, and their own material
                bits are still unread - the .ngn creature chunk (0x106) is
                where to look.
 P1.0 [DONE]    The second object section. Same record layout, stored at a
                QUARTER scale - positions and mesh vertices both x4. That
                was the stray planks and blocks around the house. The split
                is marked by section 4's leading run of pointers; zones come
                from the .ngn scene via assignZones(). tools/scene-crosscheck
                validates split, scale and zones on every scene.
                Edges left: level06/level1 (one object), level10 (two).

 P1.5 [DONE]    Portal visibility, the data and filtering half. Geometry is
                bucketed by zone as well as (page, blend, cull), so a zone is
                a set of draw groups that can be switched off without
                touching the buffers - Viewer.setVisibleZones() flips each
                group's material.visible, which three.js honours per group.
                reachableZones(portals, from) walks the graph one step: the
                zone, whatever its portals reach, and zone 0. In the viewer,
                keys 0-9 stand in a zone and `a` shows the whole level.
                Verified by eye: zone 5 is the attic, zone 1 the bedroom and
                landing, each a coherent room rather than a scatter. Level 1
                is 83 draw groups over 9 zones and 22 portals; standing in
                zone 5 draws 6,023 of 33,103 triangles.
 [READY]  Frustum-clipped portal walk. What remains of the engine's real
          algorithm: recurse through portals whose outline is inside the
          view, narrowing the frustum to each outline, instead of taking a
          fixed one-step neighbourhood. Needs the portal corners projected
          per frame; level.zones already carries them.
 [BLOCKED] Camera's own zone          <- P2. The engine tracks it as the
          player crosses portals, so it arrives with the character
          controller. Until then the zone is picked by hand.
 P1.6 [ACTIVE]  Parity harness. Half done: tools/render-level.ts now takes
                --eye/--target/--size/--fovy and matches three.js (vertical
                FOV, the viewer's clear colour, the same two draw queues and
                the same per-face culling), so browser and oracle can be
                diffed pixel for pixel from one camera. What is still
                missing is the other half - the same camera in the REAL
                game via dgVoodoo, which is the only thing that can settle
                absolute brightness. Worth doing early: with colour
                management off the level is much darker than it was, and
                that is believed right but not yet confirmed against the
                retail game.
 [OPEN]  140 faces on page 16 (mode 0x1000) in level 1 - Buzz's page.
 [OPEN]  hoola.all reports page 0, unlike every other model (16-24).
 [OPEN]  Zone / room streaming details: lazycurler/ToyStory2Research has the
         decompiled zone and boundary logic (gAdjecentZoneLUT, gBoundaryLUT).

 PHASE 2 - BUZZ MOVES
================================================================================
 Buzz is the ONLY playable character. Done means: walk, jump, double jump,
 charged laser and charged spin around Andy's House with the original feel.
 Every constant comes from the decompiled object core, not from tuning.

 P2.1 [DONE]    Extract the constants: gravity, walk/run speed, jump and
                double-jump impulses, air control, spin and laser charge
                timings, hover/fall states.
                Found: the whole controller is one cluster in toy2.exe
                (0x433700-0x436d80, entry FUN_00436220), located by
                following Buzz's sound events (BUZJMP1, BUZWING, BUZSKID)
                back to their callers. Cross-checked function by function
                against psx.exe (0x8003af24-0x8003ec30): same code, same
                constants, two differences (PC ground friction 48 vs 32,
                PC height-capped double jump). Physics is per 60 Hz tick
                in units 32x the level file's. Written up in docs/PLAYER.md
                and typed in src/sim/player-constants.ts. Ghidra scripts
                to rebuild both decompiles: tools/ghidra/.
                Not extracted: projectile speeds, the mover's step height
                and slope limit (P2.3), ledge-grab probe geometry.
 P2.2 [DONE]    Character controller on the fixed 60 Hz tick.
                src/sim/player.ts is a transcription of FUN_00436220 and
                what it calls: the jump state machine, gravity and the
                release cut, the double jump both ways, friction and the
                speed clamps, the exponential turn with its snap and skid,
                and the attack timers. src/sim/trig.ts is the 12-bit angle
                system - the game's 4096-entry sine table is exactly
                round(sin(i*2pi/4096)*0x4000), checked entry by entry, so
                it is generated rather than shipped. src/sim/input.ts is
                keyboard + gamepad with remappable bindings.
                Verified twice. tools/player-probe.ts runs the controller
                headlessly against the closed-form values the constants
                predict: 24/24, including a jump apex of exactly 17664
                game units. Then the same jump in level 1 on real collision
                gives the same 17664, and all four directions move the
                right way relative to the camera.
                Two corrections came out of the port: the analog magnitude
                scales the movement table's TOP SPEED, not acceleration,
                and the jump apex is v^2/2g - v/2 rather than v^2/2g,
                because gravity applies on the jump tick too.
                Enter toggles play. The trailing camera is a placeholder
                for P2.4 and is only there because controls are
                camera-relative.
                Groundwork DONE: key `p` stands the selected character in
                the level on real collision. Viewer.setPlayer keeps the
                level and adds the character beside it (setModel replaces
                the scene, which is right for inspecting a model and wrong
                for standing one on a floor), and collision.ts gained
                buildCollisionWorld/groundBelow - the hull flattened to
                world space and bucketed on an X/Z grid, so a ground query
                touches a handful of polys instead of 23,000.
                Confirmed in one picture: Buzz on the garage floor beside
                the car, feet on the boards at the height the collision
                reports. Geometry, textures, collision and the character
                model all agree on one coordinate system.
                Spawn point is a pickup marker for now - the real one is
                presumably in the level's own code, which is not decoded.
 P2.3 [PART DONE] Collision response against the 44-byte TERRAIN polys.
                Done so far, all geometry rather than read constants:
                slideAlongWalls() in collision.ts sweeps the horizontal step
                against unwalkable polys and slides along them, sampling the
                body at four heights rather than as a point. The death plane
                IS read from the original (see docs/PLAYER.md): fall 0x2000
                past the level's lowest terrain Y and you are put back.
                Measured on level 1, wandering 24 x 600 ticks: on the ground
                85% of the time, up from 36%.
                Three defects fixed along the way. The floor height was
                rounded, which left the player a fraction above the surface
                and so airborne every other tick. The floor query sampled
                only the tick's end point instead of sweeping. And the spawn
                heuristic scored a ring around each marker, which cannot
                tell a box top from a bedroom - it put Buzz on a surface
                with 274 cells of floor when the ground floor has 2,245.
                Still missing, and still wanting the mover read out of
                FUN_00484380: step height, the real walkable-slope threshold
                (isWalkable still guesses 45 degrees, though raising it to 89
                changes floor coverage by 0.2% so it is not urgent), and
                proper ledge handling. Walking off an edge is still how most
                falls happen.
                This is now the thing standing between the controller and
                a playable level: Buzz walks through walls and off the edge
                of the world, because the only query implemented is the
                floor one. The seam is the `Ground` interface in
                src/sim/player.ts - widen it and replace the single
                floorAt call at the end of stepPlayer.
                Read FUN_00484380 (4.7 KB, called via FUN_004855f0, which
                splits the step in two when |v|^2 > 0x400000). It holds the
                step height, wall slide and slope limit, none of which were
                extracted in P2.1.
                Original notes follow:
                single-sided, stored unit normal for slope limits, walkable
                = normal.y within the original's threshold.
                Debug draw is DONE - key `k` in the viewer, green walkable
                and red not. It confirmed what had never been checked: the
                collision file and level.dat share a coordinate system and
                scale exactly (no quarter-scale surprise), the hull sits on
                the drawn geometry, and every pickup marker in levels 1, 2
                and 5 has walkable collision beneath it (70/70, 81/81,
                77/77), floating a median 1.7-3.3 world units above it.
                Level 1: 2,363 polys, 29% walkable.
 P2.4 [BLOCKED] Follow camera            <- P2.2. Collision-aware, 4:3 native
                framing, modes as the original ("camera left/right/mode"
                strings exist in toy2.exe).
 P2.5 [MOSTLY DONE] Animation state machine.
                Found in toy2.exe: FUN_004011d0 runs a 28-state machine
                whose table is at 0x4df3f0, 20 bytes per state (byte-script
                pointer, animation slot A, slot B, playback rate, flag).
                The script is a list of frame numbers with opcodes for
                footfalls, sound events, looping and ending; a 16.16 cursor
                walks it. Generated wholesale into
                src/sim/player-animation-data.ts; the interpreter and the
                state selection are in src/sim/player-animation.ts.
                Two findings that corrected earlier docs: there is NO single
                playback rate (the 20 FPS assumption was wrong - fixed
                states run 15 or 30 script steps/sec and locomotion is
                driven by the player's actual speed), and each state names
                TWO slots because the animations are layered, the second
                supplying the bones whose tracks are -3 in the first.
                buildPosedMeshData now takes that second layer; without it
                a third of Buzz vanishes (284 triangles posed vs 417).
                Working now: idle, walk/run, jump, fall, land, double jump,
                spin, hard fall. The remaining 20 states belong to moves
                that do not exist yet (poles, zip lines, grapple, cutscenes)
                and are in the table but never selected.
                Left to do: the laser and charged-spin states, and the
                footfall/sound opcodes are counted but not yet played.
 P2.6 [READY]   Skeleton from gfx joints (0x011F) - parser done, unused.
